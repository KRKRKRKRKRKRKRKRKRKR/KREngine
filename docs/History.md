## 全体の方針(最初から変わらない物)
- **Ryusei が、すべてを理解しながら進める**(前回の DX12 エンジンは、AI に任せきりで、ブラックボックス化したため)。設計は Ryusei が決め、Claude は、選択肢と、メリット・デメリットを出して、決まった設計で書いて、解説する。
- **小さく作って、確認して、コミットする**。大きな作業は、Plan モードで計画してから。
- エンジンは、**複数のゲームで使い回す**(すれすれ飛行・Action2D・今後のゲーム)。ゲーム固有のことは、エンジンに入れない。

## 1. エンジンを、別のリポジトリに切り出した(2026-10-07〜08)
**したこと**:ゲーム「すれすれ飛行」の中にあった `Engine/` を、別リポジトリ **KREngine** にした(履歴 53 コミットを残して、`git subtree split`)。ゲームは、**Git サブモジュール**(`External/KREngine`)で使う。名前も、TenFiftyEight から **KR / KREngine** に変えた(名前空間 `KR`・マクロ `KR_`)。シェーダーは、エンジンの物(`shaders/`)にした。
**なぜ**:ほかのゲーム(Action2D など)でも、同じエンジンを使うため。ゲームごとに、コピーすると、直したところが、バラバラになる。
**決まりごと**(理由つき)
- エンジンの CMake は、**単体で動く**(`project(KREngine)`・最小のサンプル KRMinimal)。→ ゲームを作らなくても、エンジンだけで、動作を確認できる。
- ゲームのアセットの場所は、ゲームの CMake が決める(`KR_GAME_ASSETS_DIR`)。→ エンジンが、ゲームの場所を、知らなくて済む。
- ゲーム側が使うエンジンの版は、**サブモジュールが指すコミット**で決まる。→ エンジンを変えても、ゲーム側が進めるまで、ゲームは、壊れない。
**(記録なし)**:サブモジュールの代わりに、コピー・パッケージ(vcpkg など)を比べた記録は、残っていない。

## 2. ボーンアニメーション(2026-10-07 調査 → 2026-10-08 実装 A-1〜A-8)
### 2-1. 何を使うか(ライブラリの選び方)
| 選んだ物 | 選ばなかった案 | 理由 |
|---|---|---|
| **glTF 2.0**(`.glb`) | FBX・Collada・OBJ | 仕様が公開されている・Blender から、そのまま書き出せる。OBJ は、骨を持てない。FBX は、仕様が閉じていて、複雑 |
| **cgltf**(読み込み。MIT・ヘッダー 1 つ) | fastgltf・tinygltf・ufbx・Assimp | **小さくて、中身が見える**(理解しながら進める方針に合う)。スキンとアニメーションを読めると、README で確認できた。fastgltf は速いが、C++20 と、導入の手間が増える。Assimp は、何でも読めるが、大きくて重い。ufbx は、FBX が必要になったときの選択肢 |
| **再生は、自作** | ozz-animation | ozz は、本格的だが、変換の手順が増え、仕組みが中に隠れる。再生の計算は、数百行で足りる。ブレンドや IK が必要になったときに、改めて検討 |
**最初は、最低限の構成**にして、必要になったら、大きくする(Ryusei の方針)。

### 2-2. 作りの方針
- **役割を分ける(`Animation/` フォルダーを、最初から作った)**。Ryusei の判断:「あとで肥大化して、直すなら、今、対策する」。読み込み後のデータ(`Skeleton`・`AnimationClip`)は、cgltf の型を、公開ヘッダーに出さない → ローダーを替えても、ほかは変わらない。
- **座標系**:glTF(右手系)→ エンジン(左手系)は、`GltfLoader.cpp` の先頭の 3 つの関数に集めた。**Z の反転**(位置・法線・骨)と、**三角形の 2 番目と 3 番目の入れ替え**(反転で、表裏が逆になるため。OBJ と同じ決まり)。
- **スキニングのパレット**:骨ごとに「逆バインド行列 × 骨の今の世界の行列」を、CPU で先に計算する(頂点ごとに計算すると、同じ計算を何百回も繰り返すため)。GPU には、**Root Signature の 4 番目(b2)の定数バッファ**で渡す。**選ばなかった案**:ルート定数(64 DWORD の上限で、骨 4 本分しか入らない)。上限は、骨 128 本・1 フレームに骨つきの物 32 個。
- **頂点**:今の `Vertex`(48 バイト)は変えず、`MeshData` に、**並行する配列 `skin`**(骨の番号 4 つ + 重み 4 つ)を足した。骨つきの形だけ、72 バイトの頂点にして GPU に入れる。→ 骨なしの形は、今までどおり。
- **当たり判定の形(`Hitbox`)は、骨の中の座標で持つ**。骨が動いても、数字が変わらず、骨の今の行列を掛けるだけで、世界の形になる。**判定には、スキニングのパレットを、使わない**(パレットは、頂点を動かすための行列。判定は、骨そのものに付ける)。球を足した(カプセルは、必要になったら)。
- **窓口 `AnimatedModel`**:読み込み・再生・描画・判定の形を、1 つにまとめた(ゲームから見ると、手順が多すぎたため)。部品は、そのまま残した(窓口は、呼ぶだけ)。
- **判定の形の保存は、JSON(`<モデル名>.hitboxes.json`)**。骨は**名前**で探す(骨の並びが変わっても壊れない)。nlohmann/json は、エンジンの中だけ(PRIVATE)。**選ばなかった案**:コードに書く(調整のたびに、ビルドが要る)・glTF の拡張データに入れる(Blender 側の手間が大きい)。

### 2-3. 実装中に見つかった問題(理由として、残す)
| 問題 | 原因 | 対処 |
|---|---|---|
| 基準姿勢の位置が合わない(差 1.0) | Blender の書き出しは、アーマチュアのノード(骨ではない)に、Y 軸 90° の回転を持つ。親子の掛け算に、入っていなかった | 根の骨に、親のノードの世界の行列(`Joint::parentWorld`)を持たせた。起動時に、差が 0 になることを、確認するログを出す |
| 骨の名前が `ボ...` のまま出る | Blender が日本語を `\uXXXX` で書き出す。cgltf は、元の文字に戻さない | `DecodeName` で戻した |
| メッシュの中の骨が見えない(深度テストで隠れる) | 骨を、普通に描いていた | **手前に描く(`overlay`。Blender の「In Front」)**をエンジンに足した |
| 日本語を含むフォルダーで、Debug の起動直後に落ちる | CMake が埋め込む場所は UTF-8。`path(const char*)` は CP932 として読み、変換に失敗(Action2D 側で発見) | `char8_t` で `path` にする(`Utf8Path`) |
| KRMinimal が、なくなった `Test.glb` を、毎回読もうとしていた | A-1 の確認用のコードが、残っていた | 外した |

### 2-4. 骨の表示と、調整ツール
- 骨の表示を、1 ピクセルの線から、**Blender の八面体**(根もと 10% が、いちばん太い)にした。理由:線では、見えにくい(Ryusei)。選んだ骨は、色が変わる。
- 調整を、サンプルの ImGui から、**専用のツール KRAnimationEditor**に移した。Ryusei の方針:「調整は、専用のプロジェクトで行い、ゲームは、呼び出すだけ」。メリット:ゲームのコードが軽い・全ゲームで使い回せる・ゲームを動かさずに調整できる。**置き場所は、エンジンの中**(`tools/`)。選ばなかった案:別リポジトリ(エンジンとの版の同期が要る)。
- ツールが、別のゲームのフォルダーに保存できるよう、`KR::SetAssetRoot`(アセットの場所を、実行時に切り替える)と `GetCommandLineArguments` を足した。Release でも、元のフォルダーに保存できる。
- ImGui の画面は、**日本語**にした。「最近使ったフォルダー」は、独立した欄をやめて、アセットの行に統合した(Ryusei の指摘:「アセットで選んだなら、いらないのでは」)。

## 3. 版(バージョン)の付け方を決めた(2026-10-08)
**したこと**:`メジャー.マイナー.パッチ`(セマンティック バージョニング)。現在 **0.2.1**。`CHANGELOG.md`・`Versioning.md`・`KR::GetVersion`・タグ。詳しい決まりは [Versioning.md](Versioning.md)。
**なぜ**:ゲームが、「どの版のエンジンを、使っているか」を、コミットの番号ではなく、タグで言えるようにするため。進める前に、CHANGELOG の「ゲーム側で必要な変更」を読めるようにするため。
**悩んだ点**:履歴を数え直すと、A-6 以降(判定の形・`AnimatedModel`・調整ツール)は、あとから入った機能で、厳密には 0.3.0 相当。しかし、Ryusei は、「**今の状態を 0.2.1 にする**」ことを選んだ(提案の、おすすめだったため)。そこで、機能は、すべて 0.2.0 にまとめて、タグ(v0.1.0 = 切り出し・v0.2.0 = ボーンアニメーションと調整ツール・v0.2.1 = 版の仕組み)を、あとから付けた。**v0.1.0・v0.2.0 は、後付けなので、そのコードには、版を出す仕組みが無い**。
**メジャーが 0 の間は、開発中**(互換性が変わることがある)。1.0.0 は、ゲームから見える API が、落ち着いてから。

## 4. 作業の進め方を変えた(2026-10-08。Ryusei の指示)
- **ブランチ**:更新は、feature ブランチで作業し、確認のあとに、main へ merge する。push は、頼まれたときだけ。
- **理解確認の質問**:書く前の説明で止まらず、**先に作って、コードを見せてから**確認する(Ryusei:「実際のコードを見て確認したい」)。**その後(同じ日)**:Ryusei が、「詳細な MD を読めば、理解できる。理解確認の質問も、自分の言葉も、要らない」と判断した。そこで、Shared の `CLAUDE.md` から、**理解確認・自分の言葉・書く前の説明・理解の深さを削除**し、代わりに、**MD に、「なぜ」と「選ばなかった案」を書く**決まりにした(feature ブランチで作業して merge・push は頼まれたときだけ・並行作業の決まりも、ここに入れた)。

## 5. 2 つの作業を、並行して進める体制にした(2026-10-08)
**きっかけ**:Action2D から、**敵の行動を、ノードで作るエディタ**の依頼が来た(原文は、`Shared/handoff/Action2D依頼_敵AIエディタ.md`)。同時に、Ryusei から、調整ツールの強化(判定の形を、画面の上で、直接動かす・クリックで選ぶ・コピーと左右反転)の依頼があった。
**決めたこと(Ryusei の指示と選択)**
- **ブランチを分けて、並行して進め、両方が終わったら merge する**。
- ノードエディタは、大規模なので、**方針を 3 回、細かく分けて、1 つ 1 つのタスクを最小にして、ミスをなくす**(1 タスク = 1 つの成果物 + 1 つの確認)。
- **作業の場所は、`git worktree`**(選ばなかった案:1 つのフォルダーで、ブランチを切り替える → 切り替えのたびに、再ビルドが走り、ビルドの結果も混ざる)。`KREngine` の本体のフォルダーは、`main` のまま(Action2D 担当が、手元のエンジンとして使うため)。
- **merge の順番は、エディタ強化 → ノード**(強化のほうが小さい。衝突を、先に直せる)。版は、強化が 0.3.0・ノードが 0.4.0。
- **VS Code の窓(会話)を、3 つに分ける**:仲介担当(本体のフォルダー)・エディタ強化担当・ノード担当。仲介担当は、merge・版・タグ・push・衝突の調整・資料の更新をする。担当は、自分のブランチの作業だけ(merge と push は、指示があるときだけ)。理由:取り返しにくい操作を、1 か所にまとめる・会話が長くなりすぎると、細部が失われやすい・担当ごとに、短い文脈で、集中できる。役割は、`Shared/仲介担当.md`。
**ノードエディタの設計の決定**(Action2D の問い (a)〜(f) への、エンジン側の答え。提案どおり)
| 問い | 決めたこと | 理由 |
|---|---|---|
| (a) 置き場所 | 部品(`GraphEditor`・`DrawGraphDebug`)+ 別 exe のツール | 「動いている敵の今の状態を光らせる」には、**ゲームの中の窓**の形が要る。ツールだけでは足りない |
| (b) ノード画面 | imnodes(MIT・小さい・依存は ImGui だけ)。**最初に、ImGui v1.92.9b との相性を確認**(動かなければ、止めて相談) | 小さく、理解しやすい。imgui-node-editor は、高機能だが、導入するファイルが多く、1.92 との相性が未確認。自作は、操作を全部書く手間 |
| (c) 条件の表し方 | 条件も、ノード | Ryusei の例のとおり(状態と状態の間に、条件がある) |
| (d) JSON の形 | ノード(id・種類・位置・値)・線(from・to・優先順位)・開始・版・`graph` の種類 | BT への拡張と、版の違いに備える |
| (e) 状況の渡し方 | キーと値の入れ物(`Context`)。条件の値に、キー名を持たせる | ゲーム固有の型を、エンジンに入れない |
| (f) BT への拡張 | `graph` の種類を持たせて、実行部は、`Graph` / `Runner` の裏に隠す | 今回は、FSM だけ。あとで、ゲーム側の呼び出しを、変えずに、BT を足せるように |
- 距離の条件は、**横(X)が基本・縦を含めるかは設定**(Ryusei の選択)。
- 優先順位は、**ノードエディタを、先に**(Action2D の依頼。Ryusei の選択)。
**この時点の状態**:両方のブランチで、最初のタスク(エディタ強化 A1-1 = 画面の点 → レイ、ノード B1-1 = 値の型)が済んだ。続きは、それぞれの担当の窓が、引き継ぎ文書を読んで、進める。

## 6. 調整ツールの強化を、merge した(0.3.0。2026-10-09)
**したこと**:KRAnimationEditor を、画面の上で、直接操作できるようにした。**クリックで、判定の形・骨を選ぶ・ギズモで、形の移動と大きさを変える・コピーと貼り付け・左右反転して貼り付け**。担当(エディタ強化担当)が、別の窓・別のブランチ(`feature/animation-editor-gizmo`)で、17 タスクに分けて進めた。経過の詳細は、[Animation.md](Animation.md)(A1〜A5 の表)・使い方と設計の理由は、[AnimationEditor.md](AnimationEditor.md)。
**途中で、計画から変えたこと(理由)**
- **ギズモを、自作から、外部ライブラリ ImGuizmo に変えた**(Ryusei の決定。A2 まで終わったところで)。理由:移動・拡大のギズモとドラッグの操作感を、すぐに得られる。回転のギズモも付いている。選ばなかった案(自作)は、判定の形の持ち方に、そのまま合わせられ、依存が増えないが、矢印・つまみ・ホバー・ドラッグの計算を、全部書く必要がある。**ImGuizmo は、ツールだけが使う**(エンジン本体・ゲームには入らない。FetchContent・コミットの番号で固定)。デメリット(行列で扱う・右手系前提 → 左手系との変換が要る)は、`AnimationEditor.md` に書いてある。
- 切り替えのキーを、Blender に合わせて、**T = 移動 / S = 大きさ**にした(最初の予定は W / E)。
- 形を選ぶのに、**レイ**(`Camera::ScreenPointToRay` → `Raycast` / `RayToSegmentDistance`)を使った。画面に投影する案もあったが、箱・球・骨の線分を、同じ方法で扱えるレイにした。
**merge のときに、仲介担当が、したこと**:`main` に `--no-ff` で merge(衝突なし)・版 **0.3.0**・`CHANGELOG.md` の「未リリース」を「0.3.0」へ・タグ `v0.3.0`・全ターゲットのビルドと、ゲーム(すれすれ飛行)の確認。
**次**:ノード担当の作業(敵 AI のノードエディタ。版 0.4.0)が、続いている。ノード担当は、この版を、`main` から取り込む。
