# 敵の行動(Behavior)

ノードで作った行動のグラフ(状態機械 = FSM)を、保存して、読んで、毎フレーム「今の状態」を決める部分。
ノードエディタ(`KRBehaviorEditor`)と、動いている敵の「今のノード」を光らせる表示は、あとの段階で足す(下の「進み具合」)。

名前空間は `KR::Behavior`。公開ヘッダー = `include/KR/Behavior/`、非公開 = `src/Behavior/`。

## 1. 何を作るか、なぜ、エンジンの仕事か
- Action2D の敵の行動(待機・移動・攻撃)を、**コードを書き換えずに、ノードで作る**ため。エディタは、エンジンの仕事(Ryusei の決定)。ゲームは、できたデータを読んで使うだけ。
- **エンジンは、物理・移動・当たり判定を持たない**(ゲーム固有)。エンジンは「今、どの状態か」だけを返し、ゲームが、それを見て動く。ゲーム固有の型は、エンジンに入れず、汎用の値の入れ物(`Context`)で渡す。
- 調査の結論は、Action2D の `docs/EnemyAI_Research.md`。2D アクションの定番は FSM なので、まず FSM。
  - **選ばなかった案**:ビヘイビアツリー(BT)は、今回は作らない。あとで足せるよう、`Graph` に `graphType`("fsm")を持たせてある。

## 2. データの形(`Graph.h`)
| 型 | 中身 |
|---|---|
| `ParamValue` | `std::variant<float, int, bool, std::string>`。ノードの値 1 つ |
| `ParamMap` | 名前 → `ParamValue`(`std::map`。JSON に書いたとき、順番がいつも同じになる) |
| `Node` | `id`・`kind`(State / Condition)・`type`("Wait" など)・位置・`params` |
| `Link` | `from → to` と `priority` |
| `Graph` | `version`・`graphType`・`startNode`・`nodes`・`links`。`FindNode(id)`・`OutgoingLinks(id)` |
| `GraphPtr` | `shared_ptr<const Graph>`。読み込んだあとは変えず、複数の敵で共有する |

- **意味は「状態 → 条件 → 状態」**。条件は、状態と状態の間にあるノード。同じ状態から複数の条件が出ているとき、`priority` の小さい順に調べる(`OutgoingLinks` が、その順で返す。同じ priority は、links の並びのまま)。
- つながっていない状態は、その状態のまま。
- **選ばなかった案**:線に条件を持たせる(線 = 条件)。依頼が「条件は、ノードで、状態の間に置く」だったので、条件をノードにした。条件にも値(半径など)があり、エディタで同じ欄の仕組みを使えるのも、利点。
- id は、グラフの中で重ならない。消した番号は使い回さない(エディタの仕事。B4-4)。読み込みでは、重なっていたら壊れたファイルとして扱う。

## 3. ノードの種類の登録(`NodeTypes.h`)
- 種類ごとに `NodeTypeInfo { kind, type, 日本語の名前, params[ParamSpec] }` を登録する。`ParamSpec` は、名前・日本語の名前・既定値・最小・最大。**値の型は、既定値の型で決まる**。
- **なぜ登録か**:エディタが、登録から値の欄を自動で作る。種類を足すときは、`NodeTypes.cpp` の `MakeBuiltinTypes` に 1 つ書くだけ。
- 組み込みは、最初に使われたときに自動で入る(`Registry()` の初期化)。**選ばなかった案**:`RegisterBuiltinNodeTypes()` を、ゲームが呼ぶ形。呼び忘れが起きるのと、静的ライブラリでは、静的登録がリンクで落とされることがあるため。
- 重複した type・空の type は、登録しない(`false`)。

| 種類 | type | 値(既定) |
|---|---|---|
| 状態 | `Wait` | なし |
| | `Patrol` | speed 1.5 |
| | `MoveToPlayer` | speed 2.5 |
| | `Attack` | boxWidth 1.0・boxHeight 0.5・damage 1(int)・windupSeconds 0.4・activeSeconds 0.2・recoverySeconds 0.4 |
| 条件 | `PlayerWithin` | key "distanceToPlayerX"・radius 3.0・includeVertical false・keyY "distanceToPlayerY" |
| | `PlayerOutside` | 同上(radius 6.0) |
| | `TimeElapsed` | seconds 1.0 |
| | `AttackFinished` | key "attackFinished" |

既定値(特に radius と Attack の数字)は、仮の値。記録なし(依頼に指定がなかったため、実装担当が仮に決めた)。ゲームに合わせて、直してよい。

## 4. 保存と読み込み(`GraphFile.h`)
- `SaveGraph(graph, file)`:JSON(版 1)に書く。一時ファイル(`.tmp`)に書いてから置き換える = **書いている途中のファイルを、読まれない**(あとの自動再読み込みのため)。float は、いちばん短い表記(0.2 は 0.2)で書く。
- `LoadGraphFile(file, out)` → `Loaded` / `NotFound` / `Invalid`。`LoadGraph(file)` はゲーム向けで、**いつも null でないグラフ**を返す(読めなければ、エラーを出して、待機 1 つのグラフ)。
- JSON のキーは、アルファベット順に並ぶ(nlohmann/json の標準)。読み書きには影響せず、順番がいつも同じになる。**選ばなかった案**:`start` を先頭に固定する順(ordered_json)。差分が読みやすくなるが、今は必要性が小さい。
- nlohmann/json は、エンジンの中だけ(PRIVATE)。公開ヘッダーに出さない。

### 壊れたファイルの扱い(落ちない)
| 壊れ方 | 動き |
|---|---|
| ファイル無し | エラー + 待機 1 つのグラフ |
| JSON として壊れている | エラー + 待機 1 つ |
| 版が違う | エラー + 待機 1 つ(読まない) |
| 未知のノードの種類 | エラー + 待機 1 つ(ファイル全体を捨てる) |
| ノード id の重なり / 状態が 1 つも無い | エラー + 待機 1 つ |
| 値が欠けた / 型が違う | その値だけ既定値 |
| `links` が無い | 線なしとして読む |
| 開始ノードが無い・状態でない | 警告 + 最初の状態から始める |
| 存在しないノードへの線 | 警告 + その線だけ捨てる |

- **選ばなかった案**:未知の種類のノードだけを飛ばす。線が宙に浮いて、グラフの意味が変わるので、ファイル全体を捨てて安全側にした。

## 5. 状況の入れ物(`Context.h`)
- ゲームが毎フレーム、`SetFloat` / `SetInt` / `SetBool` で入れる(キー = 文字列)。`GetFloat` / `GetInt` / `GetBool(key, 既定値)`・`Has`・`Clear`。キーが無い・型が違うときは、既定値。`GetFloat` は int の値も float として読む(ゲームが `SetInt` で入れても、距離の条件が読めるように)。

## 6. 条件の評価(`src/Behavior/Condition.cpp`。非公開)
- `EvaluateCondition(node, context, timeInState)`。
- `PlayerWithin` / `PlayerOutside`:**横(X)だけの距離**が基本。`includeVertical` が true のときは、縦(`keyY`)も含めて √(x²+y²) で比べる(Ryusei の決定)。**ちょうど半径は、内側**(`距離 <= 半径` が内)。
- キーが無いときは、判定できないので、`PlayerOutside` も偽(「内でない」を「外」とはしない)。
- `TimeElapsed`:状態に入ってからの秒 `>=` seconds で真(ちょうどの秒も真)。
- `AttackFinished`:状況の `key`(既定 `attackFinished`)が true のとき真。
- **キーが無いときは、偽 + 警告を、そのキーについて 1 回だけ**出す(静的な集合で覚える。毎フレーム出すと、ログが埋まるため)。**選ばなかった案**:条件ノードごとに 1 回。同じキーを見る条件が複数あっても、原因は 1 つ(ゲームが入れ忘れ)なので、キー単位にした。ゲームを再起動するまで、同じキーの警告は、2 回目以降は出ない。


## 7. Runner(`Runner.h`。敵 1 体ぶんの「今の状態」)
- `Runner runner(graph);` で、開始ノードの状態に入った状態で作る。`GetCurrentState()` が `StateView` を返す(読むだけ)。
  - `StateView`:`GetNodeId()`・`GetType()`("Attack" など)・`GetTimeInState()`(入ってからの秒)・`EnteredThisFrame()`・値(`GetFloat("speed")` など。無い・型が違うときは既定値)。
- 開始ノードが、無い・状態でないときは、最初の状態から。状態が 1 つも無い(または null の)グラフは、待機 1 つの既定のグラフ(`MakeDefaultGraph()`)に差し替える。= **どんなグラフを渡しても、`GetCurrentState()` は、必ず意味のある状態を返す**(ゲーム側で null チェックをしなくてよい)。
- 作った直後は `EnteredThisFrame()` が true(最初の状態に「入った」ところ)。
- **なぜ `StateView` は、読むだけの小さな型か**:ゲームが見るのは「種類・値・時間」だけ。`Node` そのものを返すと、ゲームがグラフの中身(線・位置)に依存してしまう。`StateView` は Runner の中のグラフを指しているので、Update・SetGraph のあとは、取り直す。

### Update(`Runner::Update(dt, context)`)
1. 時間を `dt` だけ進める(`EnteredThisFrame()` は false に戻る)。
2. 今の状態から出る線を、**priority の小さい順**に調べる。線の先が条件ノードで、その条件が成り立つ(`EvaluateCondition`。`TimeElapsed` は、進めたあとの時間で比べる)なら、条件の出力の先の状態へ移る。
3. 移ったら、入ってからの時間を 0 に戻し、`EnteredThisFrame()` を true にして、**そこで終わる**。
- **移るのは、1 回の Update で 1 回まで**。理由:線が輪になっていて、条件がいつも真でも、1 フレームの中で止まらなくなることがない。結果として、例えば「待機 → 接近 → 移動」と「移動 → 接近 → 攻撃」の条件が同時に真でも、1 フレームに 1 状態ずつ進む(確認ログ:1 回目の Update で移動・2 回目で攻撃)。**選ばなかった案**:成り立つ限り何回でも移る(上限つき)。1 フレームの中で、状態が通り過ぎてしまい、ゲームが `EnteredThisFrame()`(攻撃の開始など)を見逃すため。
- 状態から条件を通らずに、状態へ直接つないだけの線は、使わない(条件のない移動は作らない = 意味は「状態 → 条件 → 状態」)。出力がつながっていない条件は、成り立っても移れないので、次の線を調べる。
- 出る線が無い状態は、その状態のまま(終わりの状態)。

### 分岐と優先順位・つながっていないとき(B2-6。コードの変更なし = B2-5 の作りで満たされることの確認)
- 1 つの状態から条件が複数出ているとき、**priority の小さい順**に調べ、最初に成り立ったものを選ぶ。priority が同じなら、`links` の並びの順(`OutgoingLinks` が安定ソートのため)。確認ログ:両方真のとき、priority を入れ替えると、行き先も入れ替わる(巡回 ↔ 攻撃)。片方だけ真なら、その先へ。
- つながっていないときは、**その状態のまま**:線の無い状態・状態から状態への線だけ・出力のない条件・入力のない条件(たどり着けない)。出力のない条件が先にあっても、止まらず、次の priority の線を調べる(確認ログ:攻撃へ移った)。
- つながり忘れは、エディタの検証(B4-6)が、警告として知らせる。実行側は、警告を出さずに、安全に動く。

### 差し替えと最初から(`SetGraph`・`Reset`。B2-7)
- `SetGraph(graph)`:ファイルを書き換えた直後の再読み込み用。**今の状態の id が、新しいグラフにも「状態」として残っていれば、その状態と時間を引き継ぐ**(確認ログ:移動中に速さだけ直すと、移動のまま、速さが新しい値・時間はそのまま)。無ければ(消えた・条件になった)、新しいグラフの開始の状態に戻る(時間 0・`EnteredThisFrame()` が true)。null は、待機 1 つの既定のグラフ。
- **なぜ引き継ぐか**:調整ツールで値を直すたびに、敵が待機に戻ると、動きを確かめにくい。**選ばなかった案**:いつも開始に戻す(単純だが、調整のたびに、最初から見直しになる)。
- 引き継ぐのは id だけで、種類(type)が変わっていても、状態なら引き継ぐ(エディタで種類を変えたノードも、そのまま動く)。
- `Reset()`:今のグラフの開始の状態に戻す(敵の復活・やり直し用)。

### 複数の敵で共有(B2-8。コードの変更なし = 作りで満たされることの確認)
- グラフは `shared_ptr<const Graph>`(読むだけ)で、`Runner` は、**今のノードの id・入ってからの時間・入った直後か**だけを自分で持つ。だから、同じグラフで `Runner` を何体作っても、状態は別々になる。確認ログ:同じグラフの 2 体に、遠い(10)・近い(4)の状況を入れると、片方は待機・もう片方は移動。近づいた方だけ攻撃へ移り、もう片方は待機のまま。片方の `Reset()` や、別の `Runner` の `SetGraph(nullptr)` は、ほかに影響しない。
- **なぜ const か**:ゲームが敵ごとに別のグラフを読み直すと、同じ種類の敵の数だけ、メモリとファイル読みが増える。読み込んだあとに変わらないことを型で保証して、安心して共有できるようにした。
- 状況(`Context`)は、敵ごとに、ゲームが用意する(敵ごとに距離が違うため)。

## 8. 外部ライブラリ:imnodes(B3-1)
- ノードと線を ImGui の上に描く部品(MIT ライセンス。作者 Johann Muszynski)。エディタ(`GraphEditor`)で使う。**エンジンの中だけ(PRIVATE)**。公開ヘッダーに imnodes の型を出さない = ゲームの CMake は変えなくてよい。
- 取り込み方は、stb・cgltf と同じ(`FetchContent` + zip + SHA256)。**コミット `eb36902` を固定**(取得時の master の先頭。zip の SHA256 を `CMakeLists.txt` に書いてあり、中身が変わると、取得で失敗する)。
- imnodes 自身の `CMakeLists.txt` は使わない(imgui を自分で探しに行くため、エンジンの imgui とずれる)。`SOURCE_SUBDIR` を存在しない場所にして `add_subdirectory` を飛ばし、`imnodes.cpp` 1 つを、エンジンの imgui にリンクした static ライブラリ `imnodes` にした。= ImGui は、エンジンの 1 つ(v1.92.9b)だけ。
- **選ばなかった案**:Git サブモジュール(ゲーム側のサブモジュール更新が増える)・ファイルをリポジトリに丸ごとコピー(版の更新が追いにくい)・タグ版(最新のタグの日付・ImGui v1.92 との相性は、確かめていない = 記録なし。今回は、master の先頭の 1 コミットを固定した)。
- ビルドが通ることは確認した(B3-1)。**ImGui v1.92.9b で実際に動くかは、B3-2・B3-3 で確かめる**(動かなければ、止めて相談)。

- **ズームが無いことの影響**:敵 1 体のグラフは、ノードが十数個までの想定。ズームが無くても、ノードのドラッグ・画面の移動で足りる、と見込む(実際の使い心地は、B4 で、確かめる)。
- **ズームが要るとなった場合の案**(いずれも、今は選んでいない):
  1. 別の部品に替える(imgui-node-editor は、ズームがあるが、ImGui の版との相性・取り込みの手間が、別に要る)。
  2. 自前で、ズームを足す(imnodes のソースを、触る = 固定したコミットから外れる)。
  3. ノードの文字を、`ImGui::SetWindowFontScale` などで、拡大する(ノードの大きさ・線の太さまでは、変わらない)。
- **選ばなかった案**:`GetCurrentState()` が、値のコピー(`ParamMap`)を返す。毎フレームのコピーが無駄なので、指す形にした。
