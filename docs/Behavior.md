# 敵の行動(Behavior)

ノードで作った行動のグラフ(状態機械 = FSM)を、保存して、読んで、毎フレーム「今の状態」を決める部分。
ノードエディタ(`KRBehaviorEditor`)と、動いている敵の「今のノード」を光らせる表示は、あとの段階で足す(下の「進み具合」)。

名前空間は `KR::Behavior`。公開ヘッダー = `include/KR/Behavior/`、非公開 = `src/Behavior/`。

## 1. 何を作るか、なぜ、エンジンの仕事か
- Action2D の敵の行動(待機・移動・攻撃)を、**コードを書き換えずに、ノードで作る**ため。エディタは、エンジンの仕事(Ryusei の決定)。ゲームは、できたデータを読んで使うだけ。
- **エンジンは、物理・移動・当たり判定を持たない**(ゲーム固有)。エンジンは「今、どの状態か」だけを返し、ゲームが、それを見て動く。ゲーム固有の型は、エンジンに入れず、汎用の値の入れ物(`Context`)で渡す。
- 調査の結論は、Action2D の `docs/EnemyAI_Research.md`。2D アクションの定番は FSM なので、まず FSM。
  - **選ばなかった案**:ビヘイビアツリー(BT)は、今回は作らない。あとで足せるよう、`Graph` に `graphType`("fsm")を持たせてある。

## 2. データの形(`Graph.h`)
| 型 | 中身 |
|---|---|
| `ParamValue` | `std::variant<float, int, bool, std::string>`。ノードの値 1 つ |
| `ParamMap` | 名前 → `ParamValue`(`std::map`。JSON に書いたとき、順番がいつも同じになる) |
| `Node` | `id`・`kind`(State / Condition)・`type`("Wait" など)・位置・`params` |
| `Link` | `from → to` と `priority` |
| `Graph` | `version`・`graphType`・`startNode`・`nodes`・`links`。`FindNode(id)`・`OutgoingLinks(id)` |
| `GraphPtr` | `shared_ptr<const Graph>`。読み込んだあとは変えず、複数の敵で共有する |

- **意味は「状態 → 条件 → 状態」**。条件は、状態と状態の間にあるノード。同じ状態から複数の条件が出ているとき、`priority` の小さい順に調べる(`OutgoingLinks` が、その順で返す。同じ priority は、links の並びのまま)。
- つながっていない状態は、その状態のまま。
- **選ばなかった案**:線に条件を持たせる(線 = 条件)。依頼が「条件は、ノードで、状態の間に置く」だったので、条件をノードにした。条件にも値(半径など)があり、エディタで同じ欄の仕組みを使えるのも、利点。
- id は、グラフの中で重ならない。消した番号は使い回さない(エディタの仕事。B4-4)。読み込みでは、重なっていたら壊れたファイルとして扱う。

## 3. ノードの種類の登録(`NodeTypes.h`)
- 種類ごとに `NodeTypeInfo { kind, type, 日本語の名前, params[ParamSpec] }` を登録する。`ParamSpec` は、名前・日本語の名前・既定値・最小・最大。**値の型は、既定値の型で決まる**。
- **なぜ登録か**:エディタが、登録から値の欄を自動で作る。種類を足すときは、`NodeTypes.cpp` の `MakeBuiltinTypes` に 1 つ書くだけ。
- 組み込みは、最初に使われたときに自動で入る(`Registry()` の初期化)。**選ばなかった案**:`RegisterBuiltinNodeTypes()` を、ゲームが呼ぶ形。呼び忘れが起きるのと、静的ライブラリでは、静的登録がリンクで落とされることがあるため。
- 重複した type・空の type は、登録しない(`false`)。

| 種類 | type | 値(既定) |
|---|---|---|
| 状態 | `Wait` | なし |
| | `Patrol` | speed 1.5 |
| | `MoveToPlayer` | speed 2.5 |
| | `Attack` | boxWidth 1.0・boxHeight 0.5・damage 1(int)・windupSeconds 0.4・activeSeconds 0.2・recoverySeconds 0.4 |
| 条件 | `PlayerWithin` | key "distanceToPlayerX"・radius 3.0・includeVertical false・keyY "distanceToPlayerY" |
| | `PlayerOutside` | 同上(radius 6.0) |
| | `TimeElapsed` | seconds 1.0 |
| | `AttackFinished` | key "attackFinished" |

既定値(特に radius と Attack の数字)は、仮の値。記録なし(依頼に指定がなかったため、実装担当が仮に決めた)。ゲームに合わせて、直してよい。

## 4. 保存と読み込み(`GraphFile.h`)
- `SaveGraph(graph, file)`:JSON(版 1)に書く。一時ファイル(`.tmp`)に書いてから置き換える = **書いている途中のファイルを、読まれない**(あとの自動再読み込みのため)。float は、いちばん短い表記(0.2 は 0.2)で書く。
- `LoadGraphFile(file, out)` → `Loaded` / `NotFound` / `Invalid`。`LoadGraph(file)` はゲーム向けで、**いつも null でないグラフ**を返す(読めなければ、エラーを出して、待機 1 つのグラフ)。
- JSON のキーは、アルファベット順に並ぶ(nlohmann/json の標準)。読み書きには影響せず、順番がいつも同じになる。**選ばなかった案**:`start` を先頭に固定する順(ordered_json)。差分が読みやすくなるが、今は必要性が小さい。
- nlohmann/json は、エンジンの中だけ(PRIVATE)。公開ヘッダーに出さない。

### 壊れたファイルの扱い(落ちない)
| 壊れ方 | 動き |
|---|---|
| ファイル無し | エラー + 待機 1 つのグラフ |
| JSON として壊れている | エラー + 待機 1 つ |
| 版が違う | エラー + 待機 1 つ(読まない) |
| 未知のノードの種類 | エラー + 待機 1 つ(ファイル全体を捨てる) |
| ノード id の重なり / 状態が 1 つも無い | エラー + 待機 1 つ |
| 値が欠けた / 型が違う | その値だけ既定値 |
| `links` が無い | 線なしとして読む |
| 開始ノードが無い・状態でない | 警告 + 最初の状態から始める |
| 存在しないノードへの線 | 警告 + その線だけ捨てる |

- **選ばなかった案**:未知の種類のノードだけを飛ばす。線が宙に浮いて、グラフの意味が変わるので、ファイル全体を捨てて安全側にした。

## 5. 状況の入れ物(`Context.h`)
- ゲームが毎フレーム、`SetFloat` / `SetInt` / `SetBool` で入れる(キー = 文字列)。`GetFloat` / `GetInt` / `GetBool(key, 既定値)`・`Has`・`Clear`。キーが無い・型が違うときは、既定値。`GetFloat` は int の値も float として読む(ゲームが `SetInt` で入れても、距離の条件が読めるように)。

## 6. 条件の評価(`src/Behavior/Condition.cpp`。非公開)
- `EvaluateCondition(node, context, timeInState)`。
- `PlayerWithin` / `PlayerOutside`:**横(X)だけの距離**が基本。`includeVertical` が true のときは、縦(`keyY`)も含めて √(x²+y²) で比べる(Ryusei の決定)。**ちょうど半径は、内側**(`距離 <= 半径` が内)。
- キーが無いときは、判定できないので、`PlayerOutside` も偽(「内でない」を「外」とはしない)。
- `TimeElapsed`:状態に入ってからの秒 `>=` seconds で真(ちょうどの秒も真)。
- `AttackFinished`:状況の `key`(既定 `attackFinished`)が true のとき真。
- **キーが無いときは、偽 + 警告を、そのキーについて 1 回だけ**出す(静的な集合で覚える。毎フレーム出すと、ログが埋まるため)。**選ばなかった案**:条件ノードごとに 1 回。同じキーを見る条件が複数あっても、原因は 1 つ(ゲームが入れ忘れ)なので、キー単位にした。ゲームを再起動するまで、同じキーの警告は、2 回目以降は出ない。


## 7. Runner(`Runner.h`。敵 1 体ぶんの「今の状態」)
- `Runner runner(graph);` で、開始ノードの状態に入った状態で作る。`GetCurrentState()` が `StateView` を返す(読むだけ)。
  - `StateView`:`GetNodeId()`・`GetType()`("Attack" など)・`GetTimeInState()`(入ってからの秒)・`EnteredThisFrame()`・値(`GetFloat("speed")` など。無い・型が違うときは既定値)。
- 開始ノードが、無い・状態でないときは、最初の状態から。状態が 1 つも無い(または null の)グラフは、待機 1 つの既定のグラフ(`MakeDefaultGraph()`)に差し替える。= **どんなグラフを渡しても、`GetCurrentState()` は、必ず意味のある状態を返す**(ゲーム側で null チェックをしなくてよい)。
- 作った直後は `EnteredThisFrame()` が true(最初の状態に「入った」ところ)。
- **なぜ `StateView` は、読むだけの小さな型か**:ゲームが見るのは「種類・値・時間」だけ。`Node` そのものを返すと、ゲームがグラフの中身(線・位置)に依存してしまう。`StateView` は Runner の中のグラフを指しているので、Update・SetGraph のあとは、取り直す。

### Update(`Runner::Update(dt, context)`)
1. 時間を `dt` だけ進める(`EnteredThisFrame()` は false に戻る)。
2. 今の状態から出る線を、**priority の小さい順**に調べる。線の先が条件ノードで、その条件が成り立つ(`EvaluateCondition`。`TimeElapsed` は、進めたあとの時間で比べる)なら、条件の出力の先の状態へ移る。
3. 移ったら、入ってからの時間を 0 に戻し、`EnteredThisFrame()` を true にして、**そこで終わる**。
- **移るのは、1 回の Update で 1 回まで**。理由:線が輪になっていて、条件がいつも真でも、1 フレームの中で止まらなくなることがない。結果として、例えば「待機 → 接近 → 移動」と「移動 → 接近 → 攻撃」の条件が同時に真でも、1 フレームに 1 状態ずつ進む(確認ログ:1 回目の Update で移動・2 回目で攻撃)。**選ばなかった案**:成り立つ限り何回でも移る(上限つき)。1 フレームの中で、状態が通り過ぎてしまい、ゲームが `EnteredThisFrame()`(攻撃の開始など)を見逃すため。
- 状態から条件を通らずに、状態へ直接つないだけの線は、使わない(条件のない移動は作らない = 意味は「状態 → 条件 → 状態」)。出力がつながっていない条件は、成り立っても移れないので、次の線を調べる。
- 出る線が無い状態は、その状態のまま(終わりの状態)。

### 分岐と優先順位・つながっていないとき(B2-6。コードの変更なし = B2-5 の作りで満たされることの確認)
- 1 つの状態から条件が複数出ているとき、**priority の小さい順**に調べ、最初に成り立ったものを選ぶ。priority が同じなら、`links` の並びの順(`OutgoingLinks` が安定ソートのため)。確認ログ:両方真のとき、priority を入れ替えると、行き先も入れ替わる(巡回 ↔ 攻撃)。片方だけ真なら、その先へ。
- つながっていないときは、**その状態のまま**:線の無い状態・状態から状態への線だけ・出力のない条件・入力のない条件(たどり着けない)。出力のない条件が先にあっても、止まらず、次の priority の線を調べる(確認ログ:攻撃へ移った)。
- つながり忘れは、エディタの検証(B4-6)が、警告として知らせる。実行側は、警告を出さずに、安全に動く。

### 差し替えと最初から(`SetGraph`・`Reset`。B2-7)
- `SetGraph(graph)`:ファイルを書き換えた直後の再読み込み用。**今の状態の id が、新しいグラフにも「状態」として残っていれば、その状態と時間を引き継ぐ**(確認ログ:移動中に速さだけ直すと、移動のまま、速さが新しい値・時間はそのまま)。無ければ(消えた・条件になった)、新しいグラフの開始の状態に戻る(時間 0・`EnteredThisFrame()` が true)。null は、待機 1 つの既定のグラフ。
- **なぜ引き継ぐか**:調整ツールで値を直すたびに、敵が待機に戻ると、動きを確かめにくい。**選ばなかった案**:いつも開始に戻す(単純だが、調整のたびに、最初から見直しになる)。
- 引き継ぐのは id だけで、種類(type)が変わっていても、状態なら引き継ぐ(エディタで種類を変えたノードも、そのまま動く)。
- `Reset()`:今のグラフの開始の状態に戻す(敵の復活・やり直し用)。

### 複数の敵で共有(B2-8。コードの変更なし = 作りで満たされることの確認)
- グラフは `shared_ptr<const Graph>`(読むだけ)で、`Runner` は、**今のノードの id・入ってからの時間・入った直後か**だけを自分で持つ。だから、同じグラフで `Runner` を何体作っても、状態は別々になる。確認ログ:同じグラフの 2 体に、遠い(10)・近い(4)の状況を入れると、片方は待機・もう片方は移動。近づいた方だけ攻撃へ移り、もう片方は待機のまま。片方の `Reset()` や、別の `Runner` の `SetGraph(nullptr)` は、ほかに影響しない。
- **なぜ const か**:ゲームが敵ごとに別のグラフを読み直すと、同じ種類の敵の数だけ、メモリとファイル読みが増える。読み込んだあとに変わらないことを型で保証して、安心して共有できるようにした。
- 状況(`Context`)は、敵ごとに、ゲームが用意する(敵ごとに距離が違うため)。

## 8. 外部ライブラリ:imnodes(B3-1)
- ノードと線を ImGui の上に描く部品(MIT ライセンス。作者 Johann Muszynski)。エディタ(`GraphEditor`)で使う。**エンジンの中だけ(PRIVATE)**。公開ヘッダーに imnodes の型を出さない = ゲームの CMake は変えなくてよい。
- 取り込み方は、stb・cgltf と同じ(`FetchContent` + zip + SHA256)。**コミット `eb36902` を固定**(取得時の master の先頭。zip の SHA256 を `CMakeLists.txt` に書いてあり、中身が変わると、取得で失敗する)。
- imnodes 自身の `CMakeLists.txt` は使わない(imgui を自分で探しに行くため、エンジンの imgui とずれる)。`SOURCE_SUBDIR` を存在しない場所にして `add_subdirectory` を飛ばし、`imnodes.cpp` 1 つを、エンジンの imgui にリンクした static ライブラリ `imnodes` にした。= ImGui は、エンジンの 1 つ(v1.92.9b)だけ。
- **選ばなかった案**:Git サブモジュール(ゲーム側のサブモジュール更新が増える)・ファイルをリポジトリに丸ごとコピー(版の更新が追いにくい)・タグ版(最新のタグの日付・ImGui v1.92 との相性は、確かめていない = 記録なし。今回は、master の先頭の 1 コミットを固定した)。
- ビルドが通ることは確認した(B3-1)。**ImGui v1.92.9b で実際に動くかは、B3-2・B3-3 で確かめる**(動かなければ、止めて相談)。

## 9. エディタの部品 GraphEditor(`GraphEditor.h`。B4-1〜)
- グラフを、ImGui の窓の中に、ノードと線として描く部品。窓(`ImGui::Begin / End`)は、呼ぶ側が作る。`bool Draw(Graph&)` を毎フレーム呼ぶ。編集したら true(今は、ノードを動かしたとき)。別のグラフを開いたときは `Reset()`。
- **imnodes の型は、公開ヘッダーに出さない**(pimpl。`struct Impl`)。`ImNodes::CreateContext` は、`GraphEditor` が自分で持つ(`ImGuiLayer` は、変えない)。ゲーム・ツールは、`GraphEditor` だけを使う。
- 色:状態 = 青・条件 = 緑・開始ノード = 橙の太い枠 + タイトルに「[開始]」。種類の名前は、登録の日本語の名前(未登録の type は「(未登録)」)。
- 位置:最初の 1 回だけ、グラフから imnodes に渡し、そのあとは imnodes が持つ。ドラッグで動いたら、`Node::posX/posY` に書き戻す(保存で位置が残る)。**選ばなかった案**:毎フレーム、グラフの位置を渡す(ドラッグが、効かなくなる)。
- id:imnodes の id は、ノード・ピン・線で別の空間。ピンは `node.id * 4 + 1`(入力)・`+ 2`(出力)。線の id は、並びの番号 + 1(線の追加・削除は B4-3 で扱う)。
- **ノードの中身(B4-2)**:タイトルの下に、登録(`NodeTypeInfo::params`)の順で、値の欄を自動で作る。型ごとに:float = ドラッグできる数値欄(範囲があれば、その中)・int = 整数欄・bool = チェック・string = 文字欄。変えたら `Draw` が true を返し、値は `Node::params` に、すぐ入る。同じ名前の欄が、複数のノードにあるので、ImGui の id は、`PushID(node.id)` で分ける。
- **`ParamSpec::visibleWhen`**:空でなければ、その名前の bool が true のときだけ、欄を出す(例:`keyY` は `includeVertical` が true のときだけ)。**なぜ**:使われない欄を出すと、画面が散らかり、何を設定すべきか分かりにくい。**選ばなかった案**:エディタに、`keyY` という名前を直接書いて隠す(種類を足すたびに、エディタの変更が要る = 登録 1 つで済む、という方針に反する)。
- ノードの文字欄(キー名)は、128 文字まで。
- **線のつなぎ(B4-3)**:出力ピン(右)から、入力ピン(左)へドラッグして、つなぐ。ルールは `src/Behavior/GraphEdit.cpp` の `CanAddLink`(画面から切り離して、確認ログで試せる):
  - **状態 → 条件・条件 → 状態だけ**(同じ種類どうしは、つなげない = 意味が「状態 → 条件 → 状態」だから)。
  - **条件は、入力 1 本・出力 1 本まで**(条件が、2 つの行き先を持つと、どちらへ移るかが決まらない。分岐は、状態から条件を複数出して、priority で決める)。
  - 状態は、入力も出力も、何本でもよい(出力が複数 = 分岐)。同じ線の重複・存在しない id は、不可。
  - 出力ピンどうし・入力ピンどうしは、つながらない。ルールに合わない線は、作られず、何も起きない(**警告は出さない**。選ばなかった案:メッセージ表示。ドラッグの失敗は、線が作られないことで、分かるため)。
  - 新しい線の `priority` は、同じ状態から出る線の、最後の次の番号(分岐の順番は、あとから B4-5 で入れ替えられる)。
- **線の削除**:線を選んで Delete キー・線をピンから引き離す。文字欄に入力中の Delete は、線を消さない(`WantTextInput`)。
- 確認ログ(`GraphEdit`):状態 → 状態・条件 → 条件は拒否 / 状態 → 条件・条件 → 状態は許可 / 重複は拒否 / 状態の出力は複数 OK(priority 0 → 1)/ 条件の入力 2 本目・出力 2 本目は拒否 / 存在しない id は拒否 / 消したあとは、またつなげる。画面でも、拒否(links=6 のまま)・削除(5)・追加(6)を確認した。
- **ノードの追加・削除(B4-4)**:
  - **追加**:何もない所で右クリック → 「状態」「条件」の見出しの下に、**登録されている種類の一覧**(`GetNodeTypes`)が日本語の名前で出る → 選ぶと、押した場所に置かれる(値は、登録の既定値)。種類を足すと、メニューにも自動で出る。
  - **削除**:ノードを選んで Delete キー(複数選択もできる)。**つながる線も、一緒に消える**。開始ノードを消すと、開始は「未指定」になる(Runner は、最初の状態から始める。エディタの警告は B4-6)。開始ノードが無いときに、状態を足すと、それが開始になる。
  - **id の発行(`Graph::nextNodeId`)**:ノードを足すたびに増える一方で、**消した id は、使い回さない**。`Graph` の値で、**JSON に `nextId` として保存**する。読み込みでは、ファイルの値と「今ある id の最大 + 1」の大きい方にする(古いファイルや、手で直したファイルでも、重ならない)。
  - **なぜ使い回さないか**:`Runner::SetGraph` は、id で今の状態を引き継ぐ。消したノードの id を、別の種類のノードが使うと、動いている敵が、別の状態に、そのまま入ってしまう。**選ばなかった案**:今ある id の最大 + 1(最後のノードを消して足すと、同じ id が出る)。
  - 確認ログ(`GraphEdit`):id 1・2・3 と発行 → 一番後ろを消して足すと 4(使い回さない)/ 開始ノードを消すと開始 = 0・足すと開始になる / 未登録の type は足せない(id 0)/ 保存 → 読み直し → 足しても、重ならない / 足す・消すを 10 回して、id が全部違う。画面でも、右クリックのメニュー・追加・削除(線つきを含む)を確認した。
- **開始ノードの指定・分岐の順番(B4-5)**:
  - **ノードの上で右クリック**(何もない所なら、足すメニュー。ノードの上なら、そのノードのメニュー)。状態 → 「ここから始める」(今の開始ノードには、グレーで選べない)/ 条件 → 「(条件は、開始にできない)」/ どちらも「このノードを消す」。`SetStartNode` は、状態だけを開始にできる(条件・存在しない id は不可 = 確認ログで確認)。
  - **分岐の順番**:状態から出る線が 2 本以上のとき、その状態のノードの中に「分岐の順番(上から調べる)」が出る。行ごとに、`▲`(上へ)・`▼`(下へ)・順番・行き先の条件の名前(`#id` つき)。押すと、`MoveLinkPriority` が、その線を 1 つ上 / 下の線と入れ替える。
  - **priority は、入れ替えるたびに、0, 1, 2 … の連番に振り直す**。**なぜ**:読み込んだファイルが、同じ priority の線を持っていても(手で直した・古いファイル)、「どちらが先か」が、`links` の並びの暗黙の順に、頼らず、はっきりする。**選ばなかった案**:隣の線と priority の数字だけを交換する(同じ数字が並んでいると、入れ替えても、順番が変わらない)。
  - 確認ログ(`GraphEdit`):順番を上げる・下げる / 先頭を上へ・最後を下へは、何も起きない / 同じ priority が並んでいても、連番に直して入れ替わる / **Runner で、同じ状況(近づいた距離)でも、順番を変えると、行き先が変わる**(半径の近い条件が先 → 攻撃・遠い条件が先 → 移動)。画面でも、`▲` で順番が入れ替わる・「ここから始める」で開始の印が移る・条件のメニューを確認した。
  - 右クリックで、どちらのメニューを出すかは、直前のフレームの「マウスが乗っているノード」(`ImNodes::IsNodeHovered`)で決める。
- **検証(B4-6。`GraphValidate.h` の `ValidateGraph`、画面は `GraphEditor::DrawWarnings`)**:つなぎ忘れなどを、日本語の警告の一覧にする。**警告があっても、グラフは動く**(Runner は、安全に動く)。エディタが、作る人に知らせるための物。
  | 警告 | 条件 | 動くとき |
  |---|---|---|
  | 開始なし | 開始ノードが無い・状態でない | 最初の状態から始まる |
  | 行き止まり | 状態から出る線が無い | その状態のまま、ずっと続く(終わりの状態として、わざと作ることもある) |
  | 条件の入力なし | 条件に入る線が無い | 調べられることがない |
  | 条件の出力なし | 条件から出る線が無い | 成り立っても、移れない |
  | たどり着けない状態 | 開始から、線の向きどおりにたどれない状態 | 使われない |
  - **なぜ「警告」で、エラーにしないか**:作っている途中は、つなぎ忘れが、いつも起きる(ノードを置いてから、つなぐ)。保存を止めると、途中の保存ができない。「行き止まり」は、わざと作る(例:ずっと続く状態)こともある。**選ばなかった案**:保存の拒否・エラーにする。
  - **たどり着けない条件は、警告にしない**(条件が、たどり着けない状態につながっているだけなら、その状態の警告で、足りる。入力も出力もない条件は、「入力なし」「出力なし」で出る)。
  - 確認ログ:正常なグラフ(輪になった例)は 0 件 / 開始なし(1 件)/ 行き止まり + 入力のなくなった条件(2 件)/ 孤立した条件(入力なし + 出力なし)と、出力のない条件(3 件)/ たどり着けない状態(1 件)/ 空のグラフ(開始なし 1 件)。画面でも、「警告なし」→ 開始ノードを消すと「警告 4 件」を確認した。
  - 警告を、ノードにも印として出すこと(ノードの色など)は、まだしていない(記録なし。必要なら、あとで)。
- **確認用プローブで見つけた落とし穴**:プローブが、ノードを「並びの番号(`nodes[4]`)」で読んでいて、削除で並びが変わると、別のノードの `damage` を読んで落ちた。**ノードは、並びの番号ではなく、id で探す**(`Graph::FindNode`)。エディタ本体のバグではなかった。
- 確認用の `KRGraphEditorProbe`(`probe/BehaviorProbe/`。依頼の例のグラフを描く)。ツール `KRBehaviorEditor`(B4-7)ができたら、役目を終える。

## 10. ゲームの中で、動いている敵を見る DrawGraphDebug(`GraphDebug.h`。B5-1)
- `DrawGraphDebug(runner)`(または `DrawGraphDebug(graph, runner)`):ゲームの `OnImGui` の中の、`ImGui::Begin` と `End` の間で呼ぶ。グラフを、**読むだけ**で描く(動かせない・編集できない)。
  - **光るノード = 今の状態**(橙の太い枠 + 広い半透明の枠)。**橙の線 = 今の状態から出る線**(次に移るかもしれない道)。左下に、今の状態の名前・id・**入ってからの時間**(入った直後は「★今、入った」)。
  - 状態 = 青・条件 = 緑(エディタと同じ)。各ノードに、登録の日本語の名前と、値(小数・整数 = 「名前 値」/ チェックは、true のときだけ名前/ **文字(キー名)は、出さない**)。
  - 窓の残りの広さに、グラフ全体を収める(**縮小はする・拡大はしない**。窓が小さくても、全体が見える)。`width` / `height` で、大きさを決めることもできる。
- **imnodes を使わず、ImGui の描画(`ImDrawList`)だけで描く**。**なぜ**:imnodes は、「文脈」(`ImNodes::CreateContext`)を持つ必要があり、`DrawGraphDebug` が自由な関数だと、文脈の作成・破棄を、ゲームに頼むことになる(ImGui より後に破棄すると落ちる)。読むだけの表示なら、動かす・つなぐ機能は、要らない。**選ばなかった案**:`GraphEditor` に、読み取り専用の描き方を足す(クラスを、ゲームが持つことになる。契約の `DrawGraphDebug(graph, runner)` の形から外れる)。
- **選ばなかった案**:今の状態から、次に移る「条件」も光らせる。`Runner` が、どの条件が成り立ちかけているかを、持っていない(条件の評価は、`Update` の中で、移ったときだけ)。持つには、`Runner` に、デバッグ用の状態が要る。必要になったら、あとで足す。
- 確認(`KRDebugDrawProbe`。見本のグラフ + 距離のスライダー):距離 10 → 待機が光る / 1.9 → 移動に移る(出る線が橙)/ 0.39 → 攻撃に移る / 「攻撃が終わった」→ 待機を通って、移動に戻る(距離が近いまま)。入った直後の「★今、入った」の表示も確認した。

## 11. ファイルが書き換わったら、読み直す GraphAsset(`GraphAsset.h`。B5-2)
- ツール(`KRBehaviorEditor`)で保存したら、動いているゲームの敵に、すぐ反映する仕組み。前例は、シェーダーの F10(キーを押して、読み直す)。**今回は、キーなしで、自動**:ファイルの更新時刻と大きさを、**約 0.5 秒おきに**見て、変わっていたら読み直す。
- 使い方:
  ```cpp
  KR::Behavior::GraphAsset asset;
  asset.Load(KR::GetAssetDirectory("Enemies") / "Walker.json");        // 起動時
  KR::Behavior::Runner runner(asset.GetGraph());
  uint32_t seen = asset.GetVersion();
  // 毎フレーム:
  asset.ReloadIfChanged(deltaTime);
  if (asset.GetVersion() != seen) { runner.SetGraph(asset.GetGraph()); seen = asset.GetVersion(); }
  ```
  `Runner::SetGraph` は、今の状態の id が残っていれば、その状態と時間を引き継ぐ(B2-7)。敵が複数いるときは、敵ごとに `seen` を持つ。
- **壊れたファイルは、前のグラフのまま**(エラーを出す)。**同じ壊れたファイルを、0.5 秒ごとに、読み直さない**(更新時刻・大きさの印を、「見た」ことにする。書き換わるまで待つ)。直ったら、読み直す。ファイルが消えても、前のグラフのまま(警告)。また現れたら、読み直す。
- **最初から読めない**(ファイル無し・壊れている)ときは、`Load` が false を返し、待機 1 つの既定のグラフを使う。**あとで、ファイルが直ったら、`ReloadIfChanged` が、読み直す**(ゲームを再起動しなくてよい)。`GetGraph()` は、**いつも null ではない**(`Load` の前でも)。
- **`GetVersion()`**:読み直しに成功するたびに増える。**なぜ「版の数字」か**:`ReloadIfChanged` の戻り値(true)は、呼んだ 1 回だけ。敵が複数いて、別々のタイミングで気づく(敵の生成が、あとから、など)ときは、「自分が持っているグラフは古いか」を、数字の比べ合いで、確かめられるほうが、取りこぼさない。
- **選ばなかった案**:ファイル監視の OS の仕組み(`ReadDirectoryChangesW`)。Windows 専用の部品が、エンジンに増える・保存の途中の通知を、うまく扱う手間が要る。0.5 秒おきの確認は、グラフ 1 つあたり、ほぼ負荷がない(更新時刻を読むだけ)。
- 保存の途中のファイルを、読まない:`SaveGraph` は、一時ファイルに書いてから、置き換える(B1-6)。置き換えの前後の、どちらか。
- 確認ログ:変更なし → 何も起きない / 書き換え後、0.1 秒では気づかず、0.5 秒たつと反映 / 反映後の `Runner` が、今の状態(id)を引き継ぐ / 壊す → 前のまま・版は増えない・もう一度見ても、読み直さない / 直す → 反映 / 消す → 前のまま / また作る → 反映 / `ReloadNow`(待たない)/ 最初から無い → 待機 1 つ・あとからできたら、反映 / `Load` の前の `GetGraph()` が、null でない。

## 12. サンプル KRBehavior(`samples/Behavior/`。B6-1)
- ツールで作ったグラフ(`samples/Assets/Enemies/Walker.json`)を読んで、**敵 1 体を動かす**見本。ゲームが、`KR::Behavior` を使うときの、そのままの雛形。上の窓 = プレイヤー(ダミー)の位置のスライダーと、世界の絵 / 下の窓 = `DrawGraphDebug`(今の状態のノードが光る)。
- **グラフ(`Walker.json`)**:`巡回(速さ 1.5)→ [プレイヤーが 5 m 以内] → 追う(速さ 3.0)→ [1.2 m 以内] → 攻撃(溜め 0.5 / 出ている 0.2 / 硬直 0.6 秒・箱 1.2 × 0.8・ダメージ 2)→ [攻撃が終わった] → 巡回`。**追う**から、もう 1 本、`[8 m より外] → 巡回`(見失ったら戻る。**分岐の 2 本目**。1 本目 = 攻撃へ、が先)。
- **ゲームの 1 フレーム(`OnUpdate`)**:① 状況を `Context` に入れる(`distanceToPlayerX` = 敵とプレイヤーの横の距離・`attackFinished`)→ ② `runner.Update(dt, context)` → ③ `GetCurrentState()` の**種類を見て、ゲームが動く**:`Patrol` = 左右に歩いて、壁で折り返す / `MoveToPlayer` = プレイヤーへ近づく / `Attack` = 入った最初のフレーム(`EnteredThisFrame()`)で数え始め、溜め → 出ている(箱がプレイヤーに重なれば、1 回だけヒット)→ 硬直 → 全部終わったら `attackFinished` を true にする。**速さ・秒・箱の大きさ・ダメージは、状態の値(`state.GetFloat("speed")` など)から読む**(グラフを直せば、ゲームのコードを変えずに、挙動が変わる)。
- **エンジンが持たないもの**:移動・当たり判定・攻撃の時間の数え方。これらは、ゲームの仕事(`BehaviorApp.cpp` の `OnUpdate`)。エンジンが返すのは、「今の状態の種類・値・入ってからの時間」だけ。
- ファイルの読み直し(`GraphAsset`)も、入っている(B6-2 で、実地に確かめる)。Debug では、`GetAssetDirectory("Enemies")` が、元の `samples/Assets/Enemies/` を指すので、ツールで保存すると、そのまま反映される。
- 確認:起動 → 巡回(青)→ プレイヤーが 5 m 以内で追う(橙。グラフで、追うが光り、出る 2 本の線が橙)→ 1.2 m 以内で攻撃(溜め = 橙の枠・出ている = 赤い箱と「ヒット!」・硬直 = 灰色の枠)→ 終わると巡回に戻る(近いままなら、また追って攻撃する)。ダメージ合計が、攻撃ごとに 2 ずつ増える。
- **再起動なしの反映の確認(B6-2)**:`KRBehavior` を動かしたまま、`samples/Assets/Enemies/Walker.json` を、書き換えた(Debug は、元の Assets を読むので、保存するだけで、反映される)。
  | 操作 | 結果 |
  |---|---|
  | 巡回の `speed` を 1.5 → 6.0 に書き換えて保存 | 約 0.5 秒後に、版 1 → 2。グラフのノードが「速さ 6.00」になり、敵が速く歩いて、壁で折り返した。**巡回の状態と、入ってからの時間は、そのまま**(6.01 → 7.65 秒。リセットされない)|
  | 途中で切れた JSON に、書き換える | **版は 2 のまま・前のグラフ(速さ 6.0)で、動き続けた**(エラーは、ログに出る) |
  | 元のファイルに、戻す | 版 3。速さ 1.5 に戻った(その間に、プレイヤーに近づいたので、追う状態に移っていた = 通常の動き) |
  - ゲームは、`GraphAsset::ReloadIfChanged` と、版の比べ合いの 3 行だけ(サンプルの `OnUpdate` の先頭)。ツールで保存 → すぐ、動いている敵に反映される、が、これで、実際に動くと確かめた。
  - 確認のために書き換えたサンプルのファイルは、元に戻した(リポジトリに、差分は残っていない)。
- **選ばなかった案**:`GetCurrentState()` が、値のコピー(`ParamMap`)を返す。毎フレームのコピーが無駄なので、指す形にした。
