# ボーンアニメーションの調べ物:用語・形式・ライブラリ・作り方

ボーンアニメーション(骨で、形を動かす)を、**エンジン側**に作るために、調べたことをまとめた。実装は、これを見て、決める。

## 1. 用語(まず、これだけ)

| 用語 | 意味 |
|---|---|
| **骨(ボーン / ジョイント)** | 動かすための、棒(の関節)。親子の階層(腕 → 前腕 → 手)を持つ。**スケルトン** = 骨の階層の全体 |
| **スキン(skin)** | 骨に、**頂点を、結びつける**こと。形(メッシュ)が、骨の動きに、くっついて、変形する |
| **ウェイト(重み)** | 頂点が、**どの骨に、どれだけ、引っぱられるか**。1 頂点に、最大 4 本の骨の、番号(**ジョイントの番号**)と、重み(足して 1) |
| **バインドポーズ** | 形と骨を、結びつけた、**基準の姿勢**(Tポーズなど) |
| **逆バインド行列(inverse bind matrix)** | 基準の姿勢での、**骨の行列の、逆**。「形の頂点を、骨の中の座標に、戻す」ために使う |
| **アニメーションクリップ** | 「走る」「羽ばたく」などの、1 つの動き。**時間ごとの、骨の姿勢(キーフレーム)**の並び |
| **キーフレーム・サンプラー** | ところどころの時刻の姿勢だけを、持つ。**間は、補間**する(位置・拡大は直線、**回転は、クォータニオンの slerp**)。補間の種類:STEP(階段)・LINEAR(直線)・CUBICSPLINE(なめらかな曲線) |

**スキニングの式**(1 つの頂点):

```
新しい位置 = ( w0 × J0 × IB0  +  w1 × J1 × IB1  +  w2 × J2 × IB2  +  w3 × J3 × IB3 ) × もとの位置
              w = 重み / J = その骨の、今の行列(世界) / IB = 逆バインド行列
```

「骨の今の行列 × 逆バインド行列」を、**骨ごとに、先に計算**して、並べた物を、**パレット**(行列の表)と呼ぶ。頂点シェーダーは、パレットから、行列を取って、混ぜるだけ。

## 2. ファイルの形式

| 形式 | 骨・アニメーション | 向き・不向き |
|---|---|---|
| **glTF 2.0(`.gltf` / `.glb`)** | **ある** | **おすすめ**。公開された仕様・Blender から、そのまま書き出せる・JSON + バイナリで、読みやすい・ライブラリが多い |
| FBX(`.fbx`) | ある | 昔から、よく使われる。仕様が、閉じていて、複雑。専用のライブラリが、必要 |
| OBJ(`.obj`) | **ない** | 今、自機に使っている形式。**骨を、持てない**(アニメーションには、使えない) |
| Collada(`.dae`) | ある | 古い。あまり、使われなくなった |

## 3. ライブラリ

### 3-1. ファイルを読む(ローダー)
| ライブラリ | 形式 | 特徴 | 向き・不向き |
|---|---|---|---|
| **cgltf** | glTF | **1 つのヘッダー**(C)。小さくて、読みやすい。スキン・アニメーションを、読める | 小さく、仕組みが、見える(**理解しながら進める**方針に、合う)。C のスタイル |
| **tinygltf** | glTF | ヘッダーだけ(C++)。広く使われている | 機能が、多い。JSON ライブラリを、同梱 |
| **fastgltf** | glTF | モダンな C++17。**速い**(tinygltf の、数倍〜 20 倍と、書かれている)・型が、安全 | 速さ・使いやすさを、重視するとき。やや、新しい |
| **ufbx** | FBX | **1 つの C のファイル**。FBX の、スキン・アニメーションの曲線・CPU でのスキニングまで | FBX を、読みたいとき |
| **Assimp** | たくさん(FBX・glTF・OBJ・Collada…) | 何でも、読める。**大きい**(依存・ビルドの時間が、増える) | 多くの形式を、一気に、読みたいとき。今は、大きすぎる |

### 3-2. アニメーションを、動かす(再生・補間・混ぜる)
| 選び方 | 内容 | 向き・不向き |
|---|---|---|
| **ozz-animation** | C++。**再生(サンプリング)・ブレンド・スキニングの計算・IK(ふくらはぎを曲げる計算)・マルチスレッド・SIMD**。レンダラーに、依存しない。元のファイル(glTF・FBX…)を、専用の形式に、**変換する道具**が、付いている | 本格的で、速い。ただし、**変換の手順が、増える**・仕組みが、中に隠れる(**理解しながら進める**には、遠回り) |
| **自分で作る** | 骨の階層・キーフレームの補間(slerp)・パレットの計算を、自分で書く。**数百行**で、足りる | **仕組みが、全部、見える**・エンジンの形に、ぴったり合わせられる。あとで、ブレンドなどを、足すのは、手間 |

## 4. 骨に追従する、当たり判定(ヒットボックス)

調べた結果、ゲームでは、次の方法が、一般的。

| 方法 | 内容 |
|---|---|
| **骨ごとの「簡単な形」**(カプセル・箱・球)を、骨に、くっつける | 形(メッシュ)そのものを、毎フレーム、判定するのは、重い。**骨に、結びつけた、簡単な形**を、骨の動きに、合わせて、動かす。格闘ゲームなどで、手・腕・胴・足ごとに、箱を、置くのと、同じ |
| 全体は、1 つの大きな形(カプセルなど) | 地形・壁との、移動の判定は、1 つの形で、軽く。**弾の当たり判定だけ**、骨ごとの形 |

作り方(このエンジン向けの案):
- **骨ごとの OBB**(今、エンジンに、ある。`Intersects` で、判定できる)。骨の、**今の世界の行列 × 箱の、骨の中での、位置・向き・大きさ**で、毎フレーム、世界の OBB を、作る。
- 箱の、**大きさ・位置**は、コードで、決める / モデルのファイルから、読む / ImGui で、調整して、保存する、の、どれか。
- カプセルは、今のエンジンに、**ない**(足すのは、別の作業)。

## 5. このエンジンの、現状と、足す物

| 項目 | 今 | 足す物 |
|---|---|---|
| 形の頂点 | `Vertex { position, normal, color, uv }`(48 バイト) | **骨の番号(4 つ)と、重み(4 つ)**を足した、別の頂点の形(スキンありの形) |
| モデルの読み込み | OBJ だけ(`LoadObj`) | **glTF の読み込み**(メッシュ・スキン・クリップ) |
| パイプライン | `Basic`(形)・`Sky`・`Line`。Root Signature:b0(world)・b1(フレーム)・t0(画像) | **スキン用の頂点シェーダー**(パレットを読む)・Root Signature に、**パレットの口**を足す |
| パレットを GPU に渡す | なし | 毎フレーム、**骨の行列の表**を、Upload バッファに、書く(`DrawLine` の動的な頂点の仕組み・定数バッファの、フレームごとの、複数持ちと、同じ考え) |
| 描く窓口 | `DrawMesh(形, 行列, 画像)` | `DrawSkinnedMesh(形, 行列, パレット, 画像)` のような、窓口 |
| 骨・クリップの、データ | なし | `Skeleton`・`AnimationClip`・`Animator`(時刻から、姿勢を、決める) |
| 骨の、デバッグ表示 | `DrawLine` がある | 骨を、線で描いて、**姿勢を、目で、確かめる**(とても、役に立つ) |
| 骨に追従する当たり判定 | OBB と `Intersects` が、ある | **骨ごとの OBB**(骨の行列から、世界の OBB を作る) |

## 7. エンジンとゲームを、同時に開発する手順(サブモジュール。実際に踏む)

| 場面 | 手順 |
|---|---|
| ゲームを作りながら、エンジンを直す | ゲームのフォルダーの中の、**エンジンのフォルダーで、直す** → **エンジンのリポジトリに、コミット・push** → **ゲームのリポジトリで、「エンジンの、新しい版を、使う」という、コミット**(サブモジュールの、ポインタの、更新) |
| 別の PC で、取得 | `git clone --recurse-submodules ...`。すでに、clone したなら `git submodule update --init` |
| よくある、つまずき | ① サブモジュールの中は、**特定のコミットに固定**(`detached HEAD`)。直す前に、`git checkout main` が、必要。② **エンジンを push する前に**、ゲーム側の、ポインタを、コミットすると、他の PC で、**そのコミットが、見つからない**。順番:**エンジン → ゲーム**。③ ゲームの `git pull` だけでは、サブモジュールは、更新されない(`git submodule update`) |

## 進み具合(実装の記録)

### A-1・A-2:glTF を読む(2026-10-08。ブランチ feature/gltf-loader)
- **決めたこと**:ローダー = **cgltf v1.15**(MIT。CMake の FetchContent で、版とハッシュを固定。エンジンの中だけで使う = PRIVATE)/ 置き場所 = 役割ごとに **`Animation/`** を新設(公開: `include/KR/Animation/`、非公開: `src/Animation/`)。
- **作った物**:`Skeleton.h`(骨の階層・基準姿勢・逆バインド行列)/ `AnimationClip.h`(骨ごとの、位置・向き・大きさのキー列)/ `GltfLoader.h`・`.cpp`(`LoadGltf(Assets/Models からの相対パス)` → `ModelData { mesh, skeleton, clips }`(当時の名前は `GltfModel`。FBX 対応で `ModelData` に改名))。公開のヘッダーに、cgltf の型は出さない(ローダーを替えても、ほかは変わらない)。
- **座標系**:glTF(右手系)→ このエンジン(左手系)は、Z の符号を反転(位置・法線・骨の位置)。向き(クォータニオン)は x・y を反転。行列は、Z が片方だけ関わる要素を反転。三角形は 2 番目と 3 番目を入れ替える(OBJ と同じ決まり)。変換は GltfLoader.cpp の先頭の 3 つの関数に集めた。
- **今はやらないこと**:骨の番号・重みを頂点に入れる(A-5)/ CUBICSPLINE の補間(警告して読み飛ばす)/ モーフ / メッシュのノードの変換 / 複数のスキン(最初の 1 つだけ)。
- **確認**:サンプル KRMinimal の起動時に、頂点数・骨の階層・動きの長さが、ログに出る(`samples/Assets/Models/Test/Test.glb`)。

### A-3:骨を線で描く(2026-10-08。ブランチ feature/bone-lines)
- **作った物**:`SkeletonDebug.h`・`.cpp`(`GetBindPoseWorldMatrices` = 逆バインド行列の逆行列から、基準姿勢での骨の世界の行列 / `DrawSkeleton` = 親から子へ線。根は小さな十字)。新しいサンプル **KRSkeleton**(`samples/Skeleton/`。glTF を読み、骨を黄色の線で描く。ImGui で、骨・メッシュ・回転の切り替え)。
- **骨の位置を、逆バインド行列の逆から求める理由**:メッシュと同じ座標(スキニングで使う基準)で求まり、骨の親のノードの変換(アーマチュアの置き方)に左右されない。動きの再生(A-4)では、骨の TRS を親から順に掛けて求める。
- **確認**:メッシュを消して、骨だけを見る(線は物に隠れるため)。メッシュを重ねて、骨が形の中にあるか、座標の変換(Z の反転)が合っているかを目で確かめる。
- テスト用のモデルは `samples/Assets/Models/Test/`(サンプル共通のアセット置き場に移した)。

### A-4:アニメーションの再生(2026-10-08。ブランチ feature/play-animation)
- **作った物**:`AnimationPose.h`・`.cpp`(`EvaluatePose(Skeleton, clip, time)` = ある時刻の、各骨の世界の行列)。手順:① キー列から、時刻 time の位置・向き・大きさを求める(キーの間は、位置・大きさは直線、向きは slerp。STEP は前の値のまま。範囲の外は端の値)→ ② 行列にする(大きさ → 向き → 位置)→ ③ 親の行列を掛ける。KRSkeleton に、再生(Play・Speed・Time の ImGui)を足した。
- **つまずき(大事)**:骨の親のノード(骨ではない)の変換を、掛け忘れると、基準姿勢が、逆バインド行列の逆と合わない。Blender の書き出しは、アーマチュアのノードに回転(90°)を持つ。**根の骨は、親のノードの世界の行列(`Joint::parentWorld`)を掛ける**。サンプルの起動時に、「親子の掛け算」と「逆バインド行列の逆」の差を、ログに出す(0 なら、一致)。
- 補間のキー検索は、先頭からの線形探索(キーが少ない間は、これで足りる。多くなったら、二分探索にする)。

### A-5:GPU スキニング(2026-10-08。ブランチ feature/gpu-skinning)
- **作った物**:`MeshData::skin`(`SkinVertex` = 骨の番号 4 つ + 重み 4 つ。骨なしは空)・`LoadGltf` が `JOINTS_0` / `WEIGHTS_0` を読む(重みの合計を 1 にそろえる)/ `Basic.hlsl` に `VSSkinned`(4 本の骨の行列を、重みで混ぜて、位置・法線を動かす)/ Root Signature に b2(パレットの住所。`PaletteRootIndex = 3`)/ `Renderer::DrawSkinnedMesh(mesh, world, palette, texture)` / `ComputeSkinMatrices(skeleton, pose)`(= 骨ごとに 逆バインド × 今の世界の行列)。
- **流れ**:`EvaluatePose`(骨の今の姿勢)→ `ComputeSkinMatrices`(パレット)→ `DrawSkinnedMesh`(パレットを、描画リストの表に積む)→ `ExecuteDrawList` で、フレームごとの Upload バッファに、まとめて書き、描く直前に、住所を b2 に伝える → GPU の頂点シェーダーが、頂点ごとに、パレットから 4 本の骨の行列を取って混ぜる。
- **上限**:骨 128 本(シェーダーの `MaxJoints` と、`Renderer::MaxSkinJoints`)・1 フレームに、骨つきの物 32 個(1 つのパレットは、骨の数にかかわらず、8 KB の枠)。超えたら、警告して、描かない。
- **確認**:KRSkeleton の「Bind pose」(基準姿勢。形が崩れない)と、再生(形が骨と一緒に曲がる)。

### 後始末(2026-10-08。ブランチ feature/cleanup)
- 骨・動きの名前の `\uXXXX`(Blender が日本語の名前を、こう書く)を、`DecodeName` で、元の文字に戻す(cgltf は戻さない)。
- 頂点が、存在しない骨の番号を指していたら、エラーにして、読み込みを失敗にする(骨の表の外を読んで、形が崩れるのを防ぐ)。
- 確認した:ファイルが無いときの、エラーのログと継続 / Release のビルドと起動(モデルが exe の横にコピーされる)。
- **既知の制限**(今は、直さない。必要になったら):キーの探索は、先頭からの線形探索 / CUBICSPLINE の補間は、読み飛ばす / スキンは最初の 1 つだけ / 1 頂点の骨は最大 4 本(1 組目だけ)/ 骨 128 本・1 フレームに骨つきの物 32 個まで / メッシュのノードの変換は使わない / モーフ(形の変化)は読まない。

### A-6:骨に追従する当たり判定(2026-10-08。ブランチ feature/hitbox)
- **作った物**:`Sphere` と球の判定(Physics/Collision.h)/ `Hitbox`・`EvaluateHitboxes`・`GenerateDefaultHitboxes`(Animation/Hitbox.h)/ `Renderer::DrawWireSphere`。詳しくは [Collision.md](Collision.md) の最後。
- **KRSkeleton**:判定の形が骨に追従して動く・テストの箱に触れると赤・ImGui で形を選んで、骨・形・中心・大きさを調整できる。
- **今はやらないこと**:形の保存・読み込み(A-7 で決める)/ カプセル / 粗い判定による絞り込み。

### 骨の表示を、Blender の形に(2026-10-08。ブランチ feature/bone-display)
- **`DrawSkeleton`(1 ピクセルの線)を、`BoneRenderer`(八面体の骨)に置き換えた**:骨 1 本 = 親の関節から子の関節まで。根もとから 10% のところがいちばん太く(幅 10%)・先に向かって細くなる(Blender の骨と同じ割合)。塗りつぶし(光で陰影)+ 縁の線。子が無い関節(先端)には、親の骨の 3 割の短い骨。使い方:`Create` → 毎フレーム `Draw(..., Style)` → `Destroy`。
- **選んだ骨は、色が変わる**(橙。ほかは青灰)。`Style::selectedJoint`。KRSkeleton の「Bone」スライダー(選んだ骨の判定の形も、連動して選ばれる = 黄色)。
- **手前に描く(overlay)**:メッシュの中の骨が、隠れて見えなかったので、エンジンに「深度テストなしで、ほかの物の手前に描く」を足した(`DrawMesh(..., overlay)`・`DrawLine(..., overlay)`。Blender の「In Front」)。描く順:通常の物 → 通常の線 → 手前の物 → 手前の線。骨つきの形(`DrawSkinnedMesh`)には、使えない。KRSkeleton の「Bones in front」で切り替え。

#### F8・F9 の状況と、保留(2026-10-12)
- **一致を確認した物**(起動時の確認ログ。同じモデルの `BossObstacle.glb` と `BossObstacle.fbx`):頂点数(1536)・三角形(512)・大きさ(2.00 × 12.93 × 1.26 m)・表裏・骨の数(4)・骨の名前と親・**骨どうしの相対位置**・骨ごとの重みの合計・動きの数と長さ(1.375 秒)・動く骨の数(4)・5 つの時刻の骨の位置(置き場所の差を除く)。
- **保留:「基準姿勢の位置」(glb と FBX の、モデルの座標での位置)**。理由:今の `BossObstacle.fbx` は、**ファイル自体が、アーマチュアとメッシュを、別々の場所に置いている**(ufbx の変換を使わない、生の値で確認:アーマチュア x = 3653 cm・メッシュ x = 494 cm。約 31 m 離れている)。glb は、どちらも原点にそろっている。ローダーの不具合ではなく、Blender の書き出し時の状態の違い。
  - Ryusei の判断(2026-10-12):**Blender で、アーマチュアとメッシュを原点にそろえて(Apply Transform)、FBX を書き出し直す。ローダーでは、補正しない**(ファイルの意味を変えない)。代わりに、ローダーは、骨とメッシュが離れているとき(骨からメッシュを囲む箱までの距離 > 箱の対角線の半分)、**警告を出す**(`FbxLoader.cpp`)。
  - **再確認の手順**:書き出し直した FBX が届いたら、①`BossObstacle.fbx` を差し替える ②ツールを起動して、警告「骨とメッシュが離れています」が**出ない**ことを確かめる ③確認ログ「FBX 骨の確認」の「根の骨の置き場所」が、glTF と FBX で、そろっている(どちらも原点付近)ことを確かめる ④画面で、骨・メッシュ・判定の形が、重なっていることを確かめる(`--model Test/BossObstacle/BossObstacle.fbx`)。
- **F9(ツール)**:モデル一覧に `.fbx` を足した(拡張子も表示)。`--model` で FBX を開ける。メッシュと動きの再生は、画面で確認した。**骨・判定の形は、上の保留のため、今の FBX では、メッシュから離れた所に出る**(再確認の手順 ④ で、確かめる)。
