# ライティング・シェーダーの計画書(0.16.0)

**状態:計画(2026-10-21)。作り始めるのは、Ryusei の「進めて」のあと。** ブランチ:`feature/lighting`。
Ryusei の希望:「ライティングは、ポイントライト・スポットライト・ハイライト・鏡面反射。シェーダーは未定」。17 の質問に答えてもらい(すべて、おすすめ + いくつかの変更)、範囲を決めた。この文書は、**決めたこと・理由・選ばなかった案・タスクの分け方・確認の方法**。

## 1. 決めたこと

| # | 項目 | 決定 | 理由 |
|---|---|---|---|
| Q1 | 「鏡面反射」 | **ハイライト**(光が当たった所の、つやの点)。映り込みは、しない | 映り込みは、環境マップ(空の全方位の画像)が要り、規模が大きい。ハイライトで、立体感の大部分が出る |
| Q2 | ハイライトの式 | **Blinn-Phong** | 軽く、つやの強さ・鋭さの 2 つの数だけで、調整できる。PBR(金属度・粗さ)は、材質のデータと環境光の仕組みが、増える |
| Q3 | 材質 | 新しい **`Material` 構造体**を、`DrawMesh` の、省略できる形で渡す。渡さなければ、**今までと同じ見た目** | 古いゲーム(すれすれ飛行・Action2D)を、変えずに動かすため |
| Q4 | 光の数の上限 | **点光源 16 個 + スポットライト 8 個** | 夜のコースに、点光源を、障害物ごとに置ける数。画素ごとの計算が、重くなりすぎない(クラスタードは、難しく、今は、要らない) |
| Q5 | 減衰 | **距離の 2 乗に反比例 + 範囲(`range`)でなめらかに 0** | 現実の光に近い。範囲の外は、計算しない(軽い) |
| Q6 | スポットの円錐 | **内側の角度・外側の角度(度)**。内側から外側へ、なめらかに暗くなる | 境目が、ギザギザにならない |
| Q7 | 光の渡し方 | `Lighting` に、**`pointLights` と `spotLights` の並び**を足す。`SetLighting` は、そのまま | 今の書き方(平行光・環境光)を、変えない |
| Q8 | 影 | **今回は、しない** | 別の段階。シャドウマップ(光から見た奥行きの画像)の仕組みが、要る |
| Q9 | 法線マップ | **今回は、しない** | 下の 3 つの理由(アニメ調で効果が小さい・素材が無い・頂点の形式の変更が広い) |
| Q10 | 明るさの扱い | **今のまま**(1 を超えたら、切る) | トーンマップは、画面全体の処理が、増える |
| Q11 | 確認 | **見本のアプリは、作らない。ゲームだけ**で確認(使い捨ての確認用プロジェクトは、コミットしない) | Ryusei の判断 |
| Q12 | シェーダー | ① **内蔵シェーダーを、よくする**(今回)。② **ゲームが書くシェーダー**(**次の段階**) | ① の作りを、② の土台にする |
| Q13 | ② の自由度(次の段階) | ピクセルシェーダーだけ + **ユーザーの数値 8 個** | 頂点の形式・骨つきの形との組み合わせを、エンジンが守れる |
| Q14 | 見た目の方向 | **アニメ調(トゥーン)を、先に** | Ryusei の判断。リアル寄りは、段階を 0 にすれば、同じ材質で、使える(Q18) |
| Q15 | ポストエフェクトの土台 | **今回は、作らない** | |
| Q16 | 確認するゲーム | **すれすれ飛行** | 3D で、空と障害物があり、光の見え方が分かる |
| Q17 | 進め方 | `feature/lighting`・最小のタスク・版 **0.16.0**・merge と push は、Ryusei の指示で | これまでと同じ |
| Q18 | トゥーンの範囲 | **陰影の段階分け + 鋭いハイライト**。`Material` に「段階の数」(**0 = なめらか = リアル寄りの Blinn-Phong**)。**1 つの内蔵シェーダーで切り替え**。輪郭線は、しない | 別のシェーダーを作ると、点光源・スポットの計算が、重複する |
| Q19 | 光の確認 | エンジンに **`Renderer::DrawLightGizmo`**(範囲の球・円錐の線)を足す。調整の窓(ImGui)は、ゲームの中に書く | 見本のアプリが無いので、光の範囲が見えないと、調整できない |
| Q20 | ゲーム側の作業 | すれすれ飛行の **`main` から、新しいブランチ**(別の作業フォルダー) | 担当の作業(`feature/obstacle-models` など)と、ぶつからない |
| Q21 | 影の準備 | **入れない** | 今回を小さくする。必要になったときに、作り直す |

### Q9 を「しない」理由(くわしく)
法線マップは、平らな面に、**細かい凹凸**を、画像で作る技術。次の理由で、今回は、しない。
1. **アニメ調の陰影は、光を段階に切って、平らに見せる**ので、細かい凹凸の効果が、見えにくい(Q14 の B)。
2. **法線マップの素材が、まだ無い**(HumanModel・障害物などに、無い)。Blender での作成は、あなたの手間が、増える。
3. **頂点の形式の変更が、広く影響する**:`Vertex` に、接線を足すと、OBJ・glTF・FBX の読み込み、骨つきの形、画像の置き場所、シェーダーが、全部、変わる(最小のタスクで、8〜10 個)。

## 2. 今の仕組みと、変えるところ

| 部品 | 今 | 変更 |
|---|---|---|
| `Lighting`(`include/KR/Renderer/Lighting.h`) | 平行光の向き・色・環境光 | **`PointLight`・`SpotLight`・並び**を足す(今のメンバーは、そのまま) |
| フレームごとの定数(`FrameConstants`。`Renderer.cpp` と `shaders/Common.hlsli`) | カメラ・平行光・フォグ・空 | **末尾に**、点光源 16 個・スポット 8 個・個数を足す(約 1 KB。上限 64 KB に、十分収まる)。**C++ とシェーダーで、並びを同じにする**(`static_assert` で、大きさを確認) |
| 物ごとのデータ(ルートシグネチャの `b0`) | **ワールド行列の 16 個の数だけ**(頂点シェーダー専用) | **新しい口 `b3`**(ピクセルシェーダー専用・数 12 個)に、**材質**を入れる。ルートシグネチャは、全パイプライン(空・線・骨つき・手前描き)が共有しているので、**変更の影響が広い**(合計 33 個。上限 64 個に収まる) |
| `DrawMesh`・`DrawSkinnedMesh`・`AnimatedModel::Draw` | 形・行列・画像 | **材質を渡す形を、追加**(今の形は、そのまま) |
| `Basic.hlsl` のピクセルシェーダー | 平行光の拡散 + 環境光 + 画像 + フォグ | 光の計算を、**関数に分けて**、平行光・点光源・スポットを、同じ式で足す。ハイライトとトゥーンを足す |
| 形(`Mesh.h`) | キューブ・板 | **`CreateSphereMeshData`**(球。滑らかな法線)を足す = ハイライトの確認に必要 |

**今までの見た目が、変わらないことの理由**:点光源・スポットが 0 個で、材質が既定(拡散の色 = 白・ハイライト 0・段階 0)なら、**今と、同じ式**になる。

## 3. タスク(1 タスク = 1 つの成果物 + 1 つの確認)
確認は、**使い捨ての確認用プロジェクト**(コミットしない。球・板・自作の光を置く)で、ビルドして、**画面を見る**。タスクが終わるごとに、コミットする(コミットの名前に、番号)。

### A. 土台:材質と、物ごとの受け渡し(見た目は、変わらない)
| # | 成果物 | 確認 |
|---|---|---|
| A1 | `KR/Renderer/Material.h`(`Material`:拡散の色・鏡面の色・つやの鋭さ・つやの強さ・段階の数・段階の境目のなめらかさ。**既定 = 今まで**)・`KR.h` に追加 | ビルドが通る・既定値が「今まで」になる |

## 4. 次の段階(今回は、しない)
**ゲームが書くシェーダー**(Q12 の ②)・影(平行光・点光源・スポット)・法線マップ・輪郭線・映り込み(環境マップ)・ポストエフェクト(ブルーム・トーンマップ)・クラスタード(光が数十個を超えるとき)。今回の作りは、②の土台を意識して、**光の計算を、関数に分ける**(`Common.hlsli`)。

## 5. 危ない所(先に、書いておく)
| 危ない所 | 対策 |
|---|---|
| ルートシグネチャの変更が、**全パイプライン**(空・線・骨つき・手前描き)に影響する | A2 で、**何も使わずに**、口だけ足して、**全ターゲットを、見た目の確認**。壊れたら、そこで止める |
| C++ の `FrameConstants` と、シェーダーの `cbuffer` の**並びが、ずれる**と、読む値が狂って、絵が壊れる | 並びを、**末尾に足す**・`static_assert` で大きさを確認・`Common.hlsli` を、1 か所にする(今の決まり) |
| 画素ごとのループ(16 + 8 回)の**負荷** | G4 で、フレームの時間を測る。重ければ、上限を下げる |
| 光を足しすぎて、白く飛ぶ(Q10 の A) | ゲームの調整窓で、光の強さを、調整する(トーンマップは、しない) |
| 既存の見た目を、壊す | A4・B1・C2・D2 で、**「個数 0・既定の材質なら、変わらない」**を、毎回、確認。H5 で、まとめて、確認 |

## 6. 確認の約束
- 1 タスクごとに、**ビルド**と、**画面(スクリーンショット)**を、確かめる。
- コミットは、日本語で、番号つき(例:`A1: Material 構造体`)。
- **merge と push は、Ryusei の指示のとき**だけ。版のタグ(`v0.16.0`)も、同じ。
